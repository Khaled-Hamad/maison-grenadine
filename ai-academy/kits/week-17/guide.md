# Week 17 - Define the professional problem

**Status:** teaching draft, not learner-tested. Fictional data and worked examples are labelled throughout. No production service is deployed by completing this lesson.

**Time:** 6 hours (360 learning minutes), with breaks additional. **Prerequisites:** the earlier course phases; review unfamiliar terms with the instructor.

**Materials:** this guide, the supplied workbook and diagram, a document editor or paper, and optionally an approved AI assistant. Do not buy a subscription for a lab without checking the dated cohort access plan.

## Learning outcomes

- Interview a user without collecting unnecessary personal information.
- Define a baseline, success measure and excluded uses.
- Select a feasible project and identify approvals.

## Start with a prediction

Before reading the worked solution, write what you expect to happen, what could be wrong, and what evidence you would need to trust the result. Keep the note for your final reflection.

## Learner explanations

### Start with the work

Describe the current task, its frequency, user and pain point before naming a product. Ask for the last concrete example and observe how the task is currently completed. Separate what the user says they want from the underlying problem and from your proposed solution.

### Scope a vertical slice

A minimum useful version completes one narrow journey end to end. 'Build an AI platform' is not a course project. A brief-to-approved-video package or request-to-reviewed-draft workflow is small enough to evaluate. Exclude payments, autonomous decisions and broad integrations until the simpler path works.

### Agree evidence early

Define a baseline, measurable acceptance criteria, risk owner, data permissions, budget and intended audience before building. Select one of the six project kits. The studio and capstone can evolve the same project; you do not need six parallel builds.

## Glossary

| Term | Plain-language meaning |
| --- | --- |
| Problem statement | A bounded description of a user's need and current difficulty. |
| Stakeholder | A person affected by or responsible for the workflow. |
| Scope | What the project includes and explicitly excludes. |
| Success measure | A defined observation used to judge value without inventing results. |

## Worked example

A suitable fictional brief is: help one organiser produce source-backed workshop invitations, with no autonomous sending, no personal data and a human approving every factual detail. Measure time and errors against a manual baseline. Do not promise a 50% reduction before collecting evidence.

## Guided lab

1. Read the six project briefs and select one appropriate to your profession.
2. Interview a consenting stakeholder or role-play using the supplied notes.
3. Map the current manual process and its pain point.
4. Define one user journey, exclusions and baseline measurement.
5. Document access, rights, budget and necessary reviewer approval.
6. Present the brief to a peer who must identify one scope risk.

## What to submit

- Project charter
- Interview and baseline plan
- Scope/exclusions
- Approval and resource checklist

## Offline and access-limited route

Use the supplied practice table and worked example rather than a live service. Complete the same reasoning, calculations, state traces or manual artifact. Ask a peer to challenge the result. Label the work **manual/simulated** and identify which live-tool, audio, integration, permissions or production behaviours have not been tested. Do not claim a simulated control was enforced by real software.

## Professional transfer

Choose your own professional context and write one safe adaptation: an engineering document review, a public health-education task, a campaign brief, or an art/design workflow. Name the authorised reviewer, permitted inputs and one task outside scope. Use invented data unless you have explicit permission; do not make a second full project this week.

## Self-check

1. Is a tool name a problem statement?
2. Must each learner complete six projects?
3. Does an estimated time saving establish value?

## Assessment

| Dimension | Maximum points |
| --- | --- |
| Identify a real task | 4 |
| Bound the project | 4 |
| Define measurable evidence | 4 |
| Identify authority and resources | 4 |

Provisional pass: **12/16** with no unresolved safety-critical issue. Score each dimension 0 (missing/unsafe), 1 (major gaps), 2 (partial), 3 (sound with minor omissions), or 4 (clear and evidenced). A learner may pass by honestly diagnosing a failed workflow; this is not production authorisation.

## Safety and required remediation

Use a role-play if consent or domain access is unavailable. Label invented stakeholder evidence rather than presenting it as a real interview.

Correct any unauthorised data use, fabricated evidence, hidden failure, unapproved consequential action or false claim of production testing before passing. Keep the actual release state explicit.

## Reflection

What changed after you checked the evidence? Which failure would matter most in your profession? What remains unassessed? Record one concrete improvement and one situation where you would stop.

## Instructor companion and answer guidance

Keep this section for feedback after the independent attempt. The separate instructor/pilot guide includes delivery preparation and assessment calibration.

**Expected worked result:** A suitable fictional brief is: help one organiser produce source-backed workshop invitations, with no autonomous sending, no personal data and a human approving every factual detail. Measure time and errors against a manual baseline. Do not promise a 50% reduction before collecting evidence.

**1. Is a tool name a problem statement?**

No. State the task and user need first.

**2. Must each learner complete six projects?**

No. Choose one main project; others are demonstrations or electives.

**3. Does an estimated time saving establish value?**

No. Measure against a sensible baseline.

**Facilitation:** ask the learner to point to a source, calculation, state transition or artifact supporting their conclusion. Accept defensible alternatives with explicit assumptions. Do not reward confident wording without evidence.

**Remediation:** identify the failed criterion, explain its consequence, provide a new small input, and reassess the relevant behaviour. Record what was actually observed; do not issue professional approval from a course score.
